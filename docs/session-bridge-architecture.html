普通 MCP notification 是负向对照，不是矛盾结论

#553 idle-wake 实验证明的是： 普通 logging、resource 和 tool-list notification 在 turn 结束后不会创建新模型 turn。 Claude Channels 是 Claude Code 明确定义的另一条 harness 输入协议： server 声明 experimental["claude/channel"]，再发 notifications/claude/channel。实现不得把两者混在一起。

即使专用 Channel notification 的 transport write 成功，也只代表 claim-only 事件交给客户端 队列，不代表正文已释放，更不代表模型已完成工作。因此 AgentParty delivery 继续保持 running 并续租，直到当前会话按稳定 receipt 完成 claim → accept，再调用 linked reply tool，且 REST 回帖携带原消息 reply_to 成功。

边界

  • 三条版本线分开：裸 Channel ≥ 2.1.80，完整 Marketplace Plugin ≥ 2.1.154，Cross-session ≥ 2.1.224。实际 launcher 依赖 Plugin，因此低于 2.1.154 时在模型启动前失败。
  • 组织策略拒绝 development Channels 时，由 Claude 明确报错；AgentParty 不偷偷启用 PTY 或第二个 resume 进程。
  • adapter 与 party serve 共用同身份、同频道实例锁，避免两个消费者双执行。
  • 只有服务端认证会员发给当前 target 的 claimed delivery 能进入会话；自己的消息不自唤醒。
  • 权限 relay 不在首期开放。后续必须 owner 身份绑定，不能让频道任意发送者批准本机工具。

持久状态边界

harness_issued 不是跨 adapter 通用的“正文已写入”缩写，必须结合具体 harness 解释。 Claude 的 claim-gated 路径先只发送 execution id；Codex 则在唯一 writer 真正调用 turn/start 或 turn/steer 前才进入该阶段。

Review / Compact 依靠 app-server 结构化错误 codexErrorInfo.activeTurnNotSteerable.turnKind，不解析英文错误文案。 每个 AgentParty delivery 使用稳定的 clientUserMessageId=agentparty:<delivery-id>； 本地 journal 自己去重，因为 Codex 只存这个关联字段，并不提供幂等语义。 未找到 client id 不能把原输入重发：进程硬崩溃可能落在外部副作用与持久历史之间， 所以 absence 不是“未执行”的证明，也不是安全的负向幂等证明。冷重启完成 resume + 有界全量 read 后仍缺失时，bridge 可放行仲裁器处理后续独立工作，但必须保留 terminal_unknown journal、原 delivery bearer 和 reply debt；它仍可由同一 client id 的精确晚到 completed history 结算一条 linked reply。这个解冻动作不把 delivery 标为普通 failed 或 abandoned，也不授权重发原正文。对账完成前，后续 start/steer、interrupt、review、 compact 与队列 flush 全部冻结。

thread/start、thread/resume、thread/fork 与频道 submit 共用 session lane；fork 返回的新 thread 会立即重建 arbiter。 未结算 delivery 或 waiting_owner continuation 存在时拒绝切离原 thread。 continuation 以 work_id + continuation_ref 绑定原 thread；只有精确匹配的 owner_answer 才能重新注入。linked REST reply 以 delivery identity 派生稳定 idempotency key，响应丢失时安全重试同一逻辑回复。

app-server 发给前端的审批、用户输入和 elicitation 请求会在 TUI 离线时有界保存，并在 TUI 重新完成 initialize 后重放。proxy 给每个 backend request 分配跨 generation 唯一的 frontend id，并维持双向映射；若 app-server 进程重启，即使原始 request id 从 0 复用， 旧 TUI 响应也无法命中新请求。serverRequest/resolved 同样改写回 frontend id。 恢复由 thread/resume 重新发出有效请求，完成前设为写屏障。

断线恢复、token fencing 与单活 successor

每次连接恢复都绑定当前 connection generation、delivery attempt、lease epoch 和 lease token。 例如 token 依次从 A 旋转为 B、再旋转为 C 时，延迟返回的 A 或 B 恢复结果既不能移除 C 的 recovery gate，也不能重新取得当前 delivery 所有权。journal 只有在恢复请求看到的 phase 与租约 快照仍然精确一致时，才允许发布 replay_safe；任何阶段推进或 token 变化都使旧请求失效。

Worker 保留已轮换 token 的恢复历史，用 superseded_safe 明确关闭旧 attempt， 而不是让它再次 claim。对同一逻辑 delivery，任一时刻最多只有一个 claimed / running successor；若旧的 terminal_unknown 获得精确 replay_safe，但新的 successor 已在执行，旧项必须先进入 durable queue， 等当前 successor 结算后再推进，禁止出现双活正文执行。所有 post-harness 状态都不走此重放路径， 只保留精确晚到回复能力。

Cross-session 与运行拓扑

Claude Cross-session 负责 Claude 会话之间的发现和短消息协同；AgentParty 的 Channel 与 directed-delivery 账本继续负责外部投递、领取、执行状态和 linked reply。两条链路不能互相冒充。
单身份、无模型调用的启动诊断：party bridge claude <channel> --check --json。 它分别报告 Claude 登录、Channel 权限、runtime comparison 和本地 gate 创建能力，不启动 Claude。 增量字段 blockers 会列出所有已独立确认的阻塞项；兼容字段 status 和 reason 仍只保留主阻塞项。runtime capability 探针返回 HTTP 404 时使用 worker_upgrade_required，其他失败使用 runtime_comparison_unavailable。 空数组只证明启动前提，不证明真实投递。 可选字段 claude_api_provider 保存经清理的 Claude resolved provider； cross_session_conflict_variables 只保存冲突变量名，不包含变量值。两者都是 v1 schema 的增量字段。内建 Channel 探针失败时，可选字段 channel_probe_phase 会稳定区分 authentication、identity、presence 与 identity_binding；旧式注入探针的普通错误不会被猜测分类。消费端必须允许这些字段缺省。 内建端点探针失败时，channel_probe_attempts（identity/Presence）或 runtime_probe_attempts（runtime capability）会记录实际端点调用次数：1 表示终局错误未重试， 3 表示两次有界重试都已耗尽。字段缺省表示没有内建端点尝试证据，不等于尝试了 0 次。 内建 identity、Presence 与 runtime capability HTTP 探针只对 429/5xx 按 150/500 ms 重试，且所有 尝试共用原来的五秒总时限。重复的 capability probe 仍然只做比较：不返回 peer，也不发布 topology 或候选。其他 HTTP 错误和注入探针保持单次调用。 因此 session_start_armed、peer_presence_checked、 delivery_verified 必定为 false。ready_for_launch 不能替代真实 SessionStart、在线 peer 或 marker 投递证据。退出码遵守模式语义：auto 可以降级为 channel_only 并成功，required 对同一缺口返回失败。

真实启动和 --check 都会用 Claude 子进程将继承的相同 cwd 与环境执行 claude auth status。明确未登录时返回 claude_auth_required；输出无法解析或 探针执行失败时返回 claude_auth_unavailable。真实启动在访问 Channel 和 spawn Claude 之前停止，避免预检与实际子进程读取不同的 CLAUDE_CONFIG_DIR 或 PATH。 全链路验收器给 claude --version 和 claude auth status 各设 10 秒截止时间， 同时约束进程退出和 stdout/stderr 排空。超时会终止 detached 进程组，不让 wrapper 留下 Claude 后代或卡住结构化预检结果。

Claude 官方不在 Bedrock、Claude Platform on AWS、Google Cloud Agent Platform 或 Microsoft Foundry 提供 Cross-session。bridge 从继承的 provider 变量或 claude auth status 识别到这些 provider 时返回 unsupported_provider。已解析的 apiProvider 优先，因为 Claude 已应用 settings precedence；只有该字段缺失才回退到继承 provider 变量。bridge 按官方语义处理会关闭 feature-flag evaluation 的环境变量： DISABLE_TELEMETRY 与 CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC 只要非空就返回 feature_flag_evaluation_disabled，包括值 0、false； DO_NOT_TRACK 与 DISABLE_GROWTHBOOK 只在值为 1 或 true 时关闭。父进程可见的 feature-flag 冲突会保守降级；settings 与远端 managed policy 仍可能在预检之后改变 session 的有效环境， 所以只有顶层 SessionStart arming receipt 和 Claude 当次 /list-agents 才是可用性证据。

AgentParty 的每条活跃 CLI 连接现在上报一组服务器隔离的匿名引用： node_ref 表示同一个本地 AgentParty 安装，runtime_ref 表示当前进程， workspace_ref 表示同一 Git workspace，worktree_ref 表示具体工作树。 runtime_ref 不是 Agent 身份：一个常驻进程可以托管多个不同 Agent。Worker 只把“同身份且 同 runtime_ref”当成调用者自己；不同 Agent 即使共享进程也会作为 peer 返回。 Worker 只在已鉴权的活 WebSocket 内存里保存这些引用；连接断开后立刻消失，不写 presence 行。 客户端通过鉴权的 runtime-peers v3 端点提交自己的引用和用途。topology_advisory 只返回关系，capability_probe 不返回 peer；只有 claude_cross_session 能返回 Claude display name 和候选，而且 Worker 必须先找到同 agent、同 token、同完整 topology 的唯一活 WebSocket。普通 presence、Web 页面和 party who --json 都拿不到原始引用。party who --json 只输出派生的 same_local_installation、same_workspace、same_worktree；不会把前者 改名成暗示物理主机证明的 same_node。

任务正文仍需经 claim → accept 两阶段领取。Cross-session 只能提前提醒另一个本地会话，不能替代 AgentParty 的所有权、租约、执行状态或 linked reply。跨机器消息还会经过 Anthropic 服务；这一版 只自动关联当前 Worker 返回的同本地安装候选，不把“远端可达”混进本地资源冲突判断。

Claude 的新鲜 ListAgents 行才是发送地址来源；匹配后调用 party_channel_peer_check，原样提交首轮 hint 的 agent、display_name 和 candidate_ref。 只有 availability=confirmed 才能立即复制 ListAgents 行的精确 address 发送；出现 [ref] 时连同 ref 一起使用，避免同名 in-process agent 抢占 bare name。确认后若调用了其他工具或执行了其他动作， 必须重新检查。这个复核把 AgentParty 侧的换会话竞态压到发送前，但它不把 Claude 的地址绑定交给 Worker； Claude 地址仍只来自 ListAgents。AgentParty 的本地 delivery consumer 锁仍按 server + token + channel 互斥：同一凭据不能靠随机 Claude 名称绕过 单实例保护。典型 Cross-session 协作对象是同一频道内使用不同 agent/token 的两个活会话。

Claude 原生 Cross-session 传输的真实验收入口：bun scripts/verify-claude-cross-session.ts。脚本会启动两个一次性 Claude 会话，并且只有同时观察到两个不同的唯一 system/init.session_id、receiver socket 初始化、sender 恰好调用一次 ListAgents、从其返回值取得唯一精确地址、随后恰好调用一次 SendMessage 向该地址发送随机 marker， 且该发送产生唯一、非错误的直接 result 才会继续。receiver 不再固定 sleep 20；它在一次 Bash 调用中等待 verifier 私有目录里的 0600 信号文件，harness 只在观察到上述发送 result 后创建该文件。最终还要在 receiver 唯一 system/init 后观察到 Bash result，再观察到恰好一条同 session_id 的纯文本主会话 inbound user marker。 信号文件只协调时序；通过仍同时要求 timing_barrier_intact=true、发送 result、Bash result 和入站 marker。 缺失或相同 session ID、错误或重复 result、提前 marker、重放 prompt、不是严格布尔值的 isReplay，以及 agent_id 或 parent_tool_use_id 非空的子 agent 事件都会被排除。版本检查、进程存活 或 socket 路径本身都不算消息送达证明。它不证明 AgentParty 的 topology、MCP hint 或 Channel 已在真实 Claude 会话中联通，也没有 candidate_ref 或 party_channel_peer_check 这道发送前复核；这些只能由下面的 AgentParty 全链路验收证明。 该原生验收会产生真实模型调用；两个进程退出共用同一个 60 秒总时限，任一侧非零退出会立即终止另一侧隔离进程组。 receiver 初始化使用一个 15 秒 readiness 时限；初始化前进程退出会立即失败，不再等满时限。 两个主进程退出后还会先终止仍持有 pipe 的后代，再排空证据流。失败产物保留在临时目录，成功默认清理。 正式验收前可运行 bun scripts/verify-claude-cross-session.ts --preflight-only。这条命令只执行 有截止时间的 claude --version 与 claude auth status，输出 agentparty.claude-cross-session-native-preflight.v1，并在任何 claude -p 模型会话启动前退出。 输出中的 model_calls_started=false 与 delivery_verified=false 是固定边界； blockers 会同时保留已确认未登录、认证探针不可用、不支持的 provider、feature flag 求值被禁用、 旧版本 Claude 和平台不支持等本机问题。ready 只表示本机静态前提可用，不是 Claude 注册、原生送达、 AgentParty topology 或 Worker 部署证明。 未知或重复参数仍输出同一 schema，状态为 invalid_request、 error_code=invalid_arguments，并在任何 Claude 探针前以退出码 9 结束。未分类错误输出 internal_error 和退出码 1；两种失败都不回显参数或底层异常文本。 原生完整验收的所有非 help 结果也使用 acceptance v1 schema。失败阶段只取 request|preflight|receiver_startup|execution|evidence|internal，并带稳定 error_code。 若本机前提在先前预检后变化，完整命令会嵌入一份新的 preflight 结果，且 model_calls_started=false。receiver 启动或执行阶段的原始诊断只保存在返回的证据目录中， 不进入 stdout/stderr。证据不足使用 failure_phase=evidence，不会伪装成进程失败；只有完整 live 证据才允许 delivery_verified=true。
AgentParty 全链路验收入口：先准备同一真实频道内两个不同 agent 的 0600 配置文件，再运行 party bridge claude --verify --channel … --receiver-config /path/to/receiver.json --sender-config /path/to/sender.json --receiver-cwd /path/to/receiver-worktree --sender-cwd /path/to/sender-worktree --preflight-only。 发布二进制已内置验收器，不要求源码仓库或 Bun。只有准备启动两个真实模型会话时才移除 --preflight-only。验收器通过当前这份 party 可执行文件启动两个 party bridge claude --cross-session required，不会混用另一份全局安装。所有预检结果，包括参数错误， 都固定输出 model_calls_started=false 和 delivery_verified=false。 嵌套的 lifecycle 对象复用 bridge 的 Plugin-only 检查；Plugin 缺失、禁用、版本不匹配、bundle 无效或状态不可读会进入 blockers，主状态为 plugin_lifecycle_unavailable、退出码 11， 且不会启动模型。它可以与 auth、provider、Worker 等独立问题同时出现。 完整 live 验收还会为 receiver 和 sender 各轮询最多 10 秒的频道 presence，要求 receiver_lifecycle_activity_observed=true 与 sender_lifecycle_activity_observed=true。activity 必须属于对应的 live daemon 身份，且时间不早于 该侧进程启动；历史、离线、watch/observer 或其他身份的 activity 都不能证明 Marketplace Hook 已运行。 全链路只在以下证据按顺序全部出现时通过： 两个 token 分别解析为不同 agent；顶层 SessionStart Hook 保持零 stdout，避免把验收标记写入模型上下文； bridge 在 Claude 仍运行时观察私有 arming 文件。普通启动在武装后立即向 bridge stderr 输出结构化回执； 全链路验收让 bridge 在 verifier 的 0700 私有目录中以 0600 模式独占创建回执文件，且该路径在任何 Claude probe 或子进程启动前从环境中删除，已存在的文件不会被覆盖。每条回执的 随机 apcs-... 地址和 session ID 必须分别匹配同一进程的启动行与唯一 system/init.session_id（最终分别记为 receiver_session_start_armed=true 与 sender_session_start_armed=true），并要求 distinct_claude_session_ids=true 与 distinct_bridge_addresses=true；同一 session 或同一生成地址的两份回执不能算双会话。sender 的 peers、ListAgents、peer_check、SendMessage 及其结果都必须位于 sender 唯一 system/init 之后并带同一 session_id。恰好一次工具调用仍按完整流计数，因此外来 session 的事件不能补齐步骤，外来 session 的重复调用也会让验收失败。每一步必须来自 Claude stream envelope 中 顶层、直接且单独出现的 tool_use 或 tool_result 内容块，步骤之间不能插入无关工具；嵌套仿造对象、 subagent 子事件和并行批次里的 sibling result 都不能补链。live Hook 把任何非空 agent_id 都当作子 agent； 畸形 sibling 不会被过滤掉并把批次降成单调用。sender 的 peers、ListAgents、peer_check、SendMessage 和等待边界的 result 还必须分别是完整流中该 tool-use ID 唯一且非错误的结果； 外来 session 或子 agent 中同 ID 的重复 result 会让对应阶段失效；sender 调用 party_channel_peers 并收到带 candidate_ref 的唯一 hint、随后 ListAgents 返回同名地址、 party_channel_peer_check 对原候选返回 confirmed、其 send_to 等于刚才的精确 ListAgents 地址，且没有其他工具插在确认与发送之间、 SendMessage 对该地址发送随机 marker、receiver 唯一 system/init 后恰好一条同 session_id 的纯文本主会话 inbound user 事件观察到该 marker；随后 receiver 不能直接信任入站 reply address， 必须针对 sender 独立重跑 peers、ListAgents、peer_check、SendMessage 完整链，发送另一枚 reply marker，并由 sender 唯一 system/init 后同 session 的纯文本主会话入站事件观察到。每个方向还要有一条与该次发送绑定、非错误且唯一的 SendMessage result。任一方向只看到 marker、没有对应门禁链都不能通过。 两个 cwd 参数可省略，各自默认使用 verifier 的当前目录。传入参数后，两个 bridge 子进程分别在规范化后的目录中启动。 verifier 在模型调用前计算最强关系：same_worktree、same_workspace 或 same_local_installation，并用 expected_topology_relation 报告。两个方向的 hint、复核结果和 coordination action 必须与该关系一致。verifier 能证明两个进程由本机启动；topology 关系仍是 client_asserted，不是身份或授权证明。保留的失败证据会脱敏两个 cwd 路径。 两条 headless session 都会接收入站消息，所以 verifier 通过 bridge 给两端设置 --cross-session-inbound accept；-p session 无法处理默认 hold 产生的批准对话框。 两端不靠固定 sleep 对齐时序，而是在一次 Bash 工具调用里等待 verifier 私有目录中的 0600 信号文件；harness 只有从另一端 stream 观察到匹配的、顶层单调用 SendMessage tool result 后才独占创建文件。Claude 随后在工具边界读取已经排队的消息。 信号文件只协调时序，本身不算投递证据；最终还要求 timing_barriers_intact=true，文件预先存在或无法写入都会失败。 stream 还要独立证明 receiver 的等待结果早于首个 marker、sender 的等待结果早于 reply marker；信号或孤立 marker 不能补齐这两个有序工具边界。 两个 bridge 退出共用同一个 180 秒总时限；任一侧非零退出会立即终止另一侧隔离进程组，零码退出则可先于仍在完成合法往返的另一侧。 两个 bridge 主进程都退出后，verifier 会先终止仍持有 pipe 的后代，再排空证据流，避免把父进程退出误当成完整清理。 每个 sender/receiver 的 stdout 与 stderr 分别受 8 MiB 总量、1 MiB 单行和 8192 行上限约束；任一流越界会立即停止两个隔离进程组， 返回 error_code=session_output_limit_exceeded，并只报告流名、限制类型和阈值，不把越界内容写进结果。 claude --version 与 claude auth status 的短探针另有每流 1 MiB 上限；超时或越界都会终止其 detached 进程组。 receiver 的 Claude/MCP 初始化、bridge 启动地址，以及匹配该地址与唯一 system/init.session_id 的武装回执， 共用同一个 20 秒 readiness 时限；三项未齐时 receiver 提前退出， verifier 会在启动 sender 前立即失败。 缺失/不同 session ID、重复 marker、 tool_result、重放 prompt、subagent 子事件、普通模型文本、 提前猜地址、错 hint、prompt echo 或单纯 socket 存在都不能通过。远程 server 必须使用 HTTPS； token 不进入 argv；源配置只读，运行时副本只进入 0600 临时目录且无论成功失败都删除，保留的失败证据会移除 token 与私有配置路径。 同一命令追加 --preflight-only 时不启动模型，也不要求另一条 live topology；它只验证 Claude 版本/登录状态、两个配置的身份与频道访问，以及部署端 runtime-peers 协议，适合发布前先拆开定位环境阻塞。 预检和完整验收都输出 cross_machine_policy_on_launch=explicit_approval_required；它描述 verifier 启动 bridge 时会要求的策略， 不表示该策略已经应用，更不表示两个会话位于同一台机器。 预检只把该端点的 HTTP 404 或明确返回非 v3 协议版本判为 worker_upgrade_required；鉴权、服务故障或无法解析的畸形响应会单独标成 runtime_peer_unavailable，不会伪装成升级结论。新增的 blockers 数组会同时列出全部可独立判定的 鉴权、provider、feature flag 与 runtime 阻塞，因此 auth 探针损坏、不受支持的 provider 与旧 Worker 可以一起出现。 claude_auth_status 把确认未登录的 logged_out 与探针不可用的 unavailable 分开；只有前者应提示 claude auth login。已有的 ready/auth-required/Worker/runtime 主 status 与退出码保持兼容。 输出只公开清理后的 claude_api_provider 和冲突变量名，不公开变量值。receiver 与 sender 的身份、频道访问分别用 receiver_identity/sender_identity 和 receiver_channel_access/sender_channel_access 报告。token 撤销时仍输出 JSON：主状态为 agentparty_unavailable，每一侧分别带 blocker 与 HTTP 状态；依赖身份的检查写 not_checked，不会退化成裸 FAIL 或伪装成端点故障。启动参数、配置和本机条件也使用同一份 v1 JSON：无效输入返回 invalid_request/error_code 和退出码 9；本机依赖不可用返回 environment_unavailable 和退出码 10； 未分类异常只返回 internal_error 和退出码 1，不回显配置路径、token 或底层异常全文。空数组只表示静态前提已就绪，不是注册或投递证明。 AgentParty 完整验收的所有非 help 结果使用 v2 acceptance schema。脚本在启动任一模型前执行与 --preflight-only 相同的完整静态检查；失败时嵌入该结果，并保持 model_calls_started=false。稳定的 failure_phase=request|preflight|receiver_startup|execution|evidence|internal 与 error_code 区分参数、Worker/auth/topology 前提、bridge 启动、执行和证据不足。原始 bridge 输出只进入已脱敏 token 与私有路径的证据文件；完整双向门禁链是 delivery_verified=true 的唯一来源。 模型调用前还会读取不走缓存的 /api/health：预检输出 worker_deployment_status 及 version、 40 位 commit、部署时间；远程 server 缺失或畸形 metadata 时加入 worker_deployment_unavailable，并归为 worker_upgrade_required。通过的远程 v2 验收原样写入 worker_deployment，把往返证据绑定到受测 Worker 构建。 loopback 开发环境可标为 worker_deployment_status=development_unversioned 后继续，但这不是发布证明。 Worker 发布脚本先用 runtime smoke agent token 调用 /api/me 和频道列表，并检查发布机具备 WebSocket 客户端； 具名 agent、目标频道访问和本地客户端都确认后，才开始迁移或 deploy。这个阶段输出 protocol_checked=false。部署后，脚本临时建立两条已鉴权 WebSocket， 使用同一个随机 node_ref 和不同 workspace/worktree 引用。每端的 topology hello 都要经过 应用队列 ping/pong 顺序屏障；随后只接受 v3、caller_binding=live_socket，以及唯一可寻址的 same_local_installation Claude 候选。脚本等待两条连接在有限时限内完成关闭握手，输出 sockets_closed=true 后才继续写路径 smoke； 响应不得包含请求侧的四类原始 topology ref。这能证明线上 Worker 的 live-socket 绑定、拓扑比较和引用脱敏， 但没有发送 Channel 或 Claude 消息，不能算 Cross-session 投递证据。 --capability-only 只保留为较弱的空 peer 端点诊断。 本地发布只检查会进入 Worker bundle 或静态资源的源码范围，但同时覆盖未跟踪文件；这既防止未记录代码借用旧 commit 发布， 也不会让 CLI、文档等非部署改动卡住 Worker 发布。
